## 2. 需求梳理

| 编号 | 需求 | 验收要点 |
|------|------|----------|
| GR1 | 首启自动触发引导，仅一次 | 新装首次打开即进引导；完成后不再出现；跳过后不再主动出现 |
| GR2 | 基础信息填写与基础消耗计算 | 性别/年龄/身高/体重/活动量 → 实时显示 BMR、每日基础消耗、参考总消耗；保存后与设置页口径一致 |
| GR3 | 饮食计划录入，两种模式 | 逐条录入每餐（餐类/名称/时间/星期）；或一次性录入当天全部餐食（一句话）；支持运动条目 |
| GR4 | AI 创造计划 | 输入内容 → AI 生成结构化计划（补全时间、估算热量、拆分餐次）；校验复用现有管线；失败可重试可降级手动 |
| GR5 | 确认前逐条编辑 + AI 重算 | 每条计划可编辑（名称/时间/热量/星期/删除）；改动后可单条或全部 AI 重估摄入/消耗；汇总实时刷新 |
| GR6 | 确认后正常使用 | 经现有 importPlan 写入计划、提醒立即调度、跳转今日页；**后续所有功能零改动** |
| GR7 | 加餐与加练使用引导 | 以「使用指引」归档图文承载（不改动加餐页/今日页） |
| GR8 | 真实截图制作指引 | 本地启动页面（H5）截取真实界面图，图文指引使用真实截图 |
| GR9 | 设置页指引归档 | 设置 → 使用指引：全部指引条目列表 + 图文详情，可重复查看 |
| GR10 | 边界与兼容 | 老用户升级不弹引导；AI 失败可全程手动兜底 |
| GR11 | **范围约束：现有功能零修改** | 除 §8 列出的 3 个最小接入点外，现有文件一行不改；现有页面交互与展示与改动前完全一致 |

## 3. 首次使用判断逻辑（回答「用是否填写基础信息判断」）

主人的思路（填没填基础信息 = 是否首次）方向正确，且现有代码已有天然抓手：`settings.bmr` 默认为 `0`，只要走一次公式估算就会 `> 0`（设置页估算器保存时写入）。**但单独用它承担「是否首次」判断有三个漏洞**：

| 场景 | 只看 bmr>0 的结果 | 问题 |
|------|-------------------|------|
| 用户在设置页手填过 TDEE，没点公式估算 | bmr=0 → 判定「首次」 | 误弹引导 |
| 用户在引导里填了基础信息但中途放弃计划 | bmr>0 → 判定「非首次」 | 「填过信息」≠「完成引导」，语义混淆 |
| 判断依据散落在 settings 各字段 | 隐式耦合 | 漏一个字段判断就失效 |

**推荐方案：独立存储键上的显式标记为主 + 基础信息为辅**（不往 settings 里加字段，settings.js 零改动）：

```
显示引导 = !onboardingState.done 且 !isLegacyUser()
```

- 新增独立存储键 `onboardingState`（由新增文件 `store/onboarding.js` 读写，现有 store 不碰）：

```ts
{ done: boolean,       // 仅在引导最终「确认完成」或用户主动「跳过」时置 true
  profile: {           // 引导收集的基础信息（引导自己用）
    gender, age, height, weight, activity
  } }
```

- `settings.bmr > 0`：作为「基础信息是否已填」的辅助参考（引导 Step1 预填判断），不承担首次判定。
- 老用户升级兼容（`isLegacyUser`，一次性检测，引导模块内执行）：

```js
// 以下任一命中即视为老用户，静默置 done = true，绝不打扰
isLegacyUser = hasPlan()
  || Object.keys(checkRecords).length > 0
  || settings.bmr > 0
  || !!settings.ai.apiKey
```

- 「清空全部数据」**不修改** `clearAll()`（零触碰）：清空后 `done` 仍为 true，不会自动重弹引导；想重新走引导 → 设置 → 使用指引 →「重新体验首次引导」（见 §6.3）。语义说明：清空是「数据复位」，引导重看是「主动行为」，二者解耦，避免为边界场景修改现有功能。

### Step1 基础信息与每日基础消耗

```
┌──────────────────────────────┐
│ ① 你的基础信息                  │
│ 性别   (女)(男)                 │
│ 年龄   [30] 岁                  │
│ 身高   [175] cm                 │
│ 体重   [74] kg                  │
│ 日常活动量 (久坐)(轻度)(中度)(高强度)│
│                              │
│ ┌ 换算结果（实时）──────────┐   │
│ │ 基础代谢 BMR      ≈1660   │   │
│ │ 每日基础消耗(不含运动) ≈1990 │  │
│ │ 参考总消耗(含日常活动) ≈2280 │  │
│ └────────────────────────┘   │
│ ② 每日目标摄入                  │
│ [1880] kcal  ← 已按参考总消耗-400 │
│   推荐，可修改。缺口=基础消耗+运动  │
│   -摄入，建议缺口 300~800        │
│                              │
│ [ 上一步 ]      [ 保存并继续 ]    │
└──────────────────────────────┘
```

交互与口径：

- 字段与设置页估算器弹层**同参数同口径**，但 UI 是引导页内新写的（不碰设置页）；计算**直接 import 现有 `estimateBmr`**（settings.js 已导出），保证两处口径一致。
- 实时计算三行结果：BMR、每日基础消耗 = BMR×1.2（不含运动，与统计口径 `baseBurn` 一致）、参考总消耗 = BMR×活动系数。
- 推荐目标摄入 = 参考总消耗 − 400（约每周减 0.4 kg），下限保护：女 1200 / 男 1500，可手改；文案解释缺口含义（与 FR4.6 着色语义一致：300~800 绿色区间）。
- 「保存并继续」调用**现有** `settings.update()` 写入 `tdee`（=基础消耗）、`bmr`、`dailyCalorieTarget`；`profile` 存 `onboardingState`。现有 store/store 文件零改动。
- 可选填「当前体重 → 目标体重」（随计划草稿经 `importPlan` 写入 `plan.meta`，不单独动 store）。

### Step2 计划录入（两种模式）

页面顶部模式切换：「✍️ 逐条录入」｜「📝 整日一句话」。两种模式产出同一份「草稿计划」，可来回切换不丢数据。

**模式 A：逐条录入（每餐一条 / 运动一条）**

```
┌──────────────────────────────┐
│ ② 你的计划（2 条）               │
│ ┌ 🍚 早餐 ────────────────┐   │
│ │ 名称 [两个包子+一杯豆浆]     │  │
│ │ 时间 [07:30]  星期 [每天▾]  │  │
│ │ 热量 [≈500 手填] [✨AI估]   │  │
│ └────────────────────────┘   │
│ ┌ 🏃 运动 ────────────────┐   │
│ │ 项目 [快走 40 分钟]         │  │
│ │ 时间 [18:30]  星期 [一三五]  │  │
│ │ 消耗 [≈180] [✨AI估]        │  │
│ └────────────────────────┘   │
│ [＋ 加一餐] [＋ 加运动]          │
│                              │
│ [ 上一步 ]   [ ✨生成我的计划 ]   │
│     没配 AI？直接 [手动完成 →]    │
└──────────────────────────────┘
```

- 餐类选择：早餐/午餐/晚餐/加餐（emoji + 徽标样式）；时间按餐类给默认值（07:30/12:00/18:00/15:30），可改。
- 星期默认「每天」，点开 chips 多选周一~周日（对应 `days` 字段）。
- 「✨ AI 估」：直接调用**现有导出** `queryCalorie`（餐食）与 `estimateBurn`（运动，带 Step1 体重，估算更准）；未配 Key 时该按钮点击弹引导页自带的配置弹层（见 Step3）。
- 「手动完成」：不调用 AI，已填条目直接进 Step4 确认（热量空则标记「自由餐」，与 `calories: null` 语义一致）。

**模式 B：整日一句话（一次性录入当天餐食）**

```
┌──────────────────────────────┐
│ ② 一句话写下今天想吃的            │
│ ┌────────────────────────┐  │
│ │早上两个包子一杯豆浆，中午食  │  │
│ │堂两荤一素一米饭，下午一个苹  │  │
│ │果，晚上青椒炒鸡胸肉，晚上八  │  │
│ │点半快走40分钟               │  │
│ └────────────────────────┘  │
│ 💡 写清大致吃什么、几点吃就行，    │
│    AI 会拆成条目并估算热量        │
│                              │
│ [ 上一步 ]   [ ✨生成我的计划 ]   │
└──────────────────────────────┘
```

- AI 一次请求完成：拆分餐次（含加餐）、配建议时间、估算每条热量、识别运动条目并估消耗。
- 这就是「一次性录入当天的餐食」模式；生成的仍是**周期计划**（默认每天生效），编辑步可改星期。
- 输出后同样进 Step4 编辑确认。

### Step3 AI 创造计划

前置：检测 `hasAIConfig()`（现有导出，直接用）。

- **已配置** → 直接调用。
- **未配置** → **引导页自带的精简配置弹层**（决策 D4；独立实现在 onboarding 页面内部，不改设置页任何代码）：

```
┌──────────────────────────────┐
│ 配置 AI，让计划自动生成           │
│ 服务商 [DeepSeek ▾]（自动填地址）  │
│ API Key [sk-________]           │
│ [ 测试连接 ]                    │
│ [ 保存并生成 ]  [ 暂不，手动模式 ]  │
└──────────────────────────────┘
```

- 配置弹层调用**现有** `switchProvider` / `updateAI` / `testAI`（均已导出）完成保存与测试，引导页只写自己的 UI。
- 「暂不，手动模式」→ 不配置，回 Step2 逐条手填完成。
- 备选实现（若评审偏好更少代码）：弹 modal 提示「需要先配置 AI」→ `uni.navigateTo('/pages/index/index')` + `app.activeTab = 'settings'`，用户在设置页配好后返回引导继续（与现有加餐页「去设置」模式同款）；代价是流程跳出一层。默认推荐页内弹层。

调用与容错：

- 新增 prompt `GUIDE_PLAN_PROMPT` 与函数 `generatePlanFromInput(input, profile)`：输入 = 用户文本/条目列表 + 基础信息（体重、目标摄入），输出 = 与 `import-format.md` 完全一致的 `{ meta, meals, exercises }` JSON；`meta` 中 `dailyCalorieTarget`/`tdee` 用 Step1 结果回填。
- **落点（追加式扩展，不动现有函数）**：函数追加在 `utils/ai.js` 末尾（复用其内部 `chat`/`extractJsonObj`/HTTP 容错/用量统计，避免复制 60 行请求代码），**现有函数一行不改**；若评审要求文件级零触碰，备选独立 `utils/ai-guide.js` 自带精简请求实现（代价是双份请求逻辑）。默认推荐前者。
- 返回值过现有 `normalizePlan` + 导入页同款校验规则（复用 `utils/plan.js`），字段缺失自动补默认（id、reminder:true 等）。
- 失败处理：自动重试 1 次 → 仍失败展示中文错误 +「重试 / 改用手动模式」双按钮；原始输入文本保留不丢。
- 生成中 loading 态：进度文案轮播（「正在拆分餐次…」「正在估算热量…」），提示保持本页（10~30 秒）。

### Step4 确认前编辑 + AI 重算（核心步）

```
┌──────────────────────────────┐
│ ③ 检查并调整你的计划              │
│ ┌ 汇总条 ─────────────────┐   │
│ │ 摄入 Σ1450 · 消耗 Σ180    │   │
│ │ 预计缺口 +720（绿色）       │   │
│ │ 基础消耗 1990 | 目标 1880   │  │
│ └────────────────────────┘   │
│ ┌ 🍚 早餐 07:30 · 每天 ──────┐  │
│ │ 两个包子+一杯豆浆             │
│ │ ≈500 kcal  [✎编辑][↻AI重估][🗑]│
│ └────────────────────────┘   │
│ ┌ 🏃 运动 18:30 · 一三五 ─────┐  │
│ │ 快走 40 分钟 ≈180 kcal       │
│ │ [✎编辑][↻AI重估][🗑]          │
│ └────────────────────────┘   │
│   …全部条目…                    │
│ [＋ 再加一餐] [＋ 再加运动]       │
│ [↻ 全部 AI 重估]                │
│                              │
│ [ 返回修改 ]  [✓ 确认完成，开始用] │
└──────────────────────────────┘
```

交互要点：

- **每条可编辑**：点「✎编辑」展开行内表单（名称/时间/星期 chips/热量或时长/餐类）；改动后该条标 `dirty`，「↻AI重估」按钮高亮提示。
- **AI 重算摄入或消耗**（GR5 核心）——**全部复用现有导出函数，utils 零新增**：
  - 餐食条目重估 = `queryCalorie(名称+备注)` → 回填热量；运动条目重估 = `estimateBurn(描述, 体重)` → 回填消耗。
  - 「↻ 全部 AI 重估」：对所有 `dirty` 条目并发 2 路逐条重估（v1 不做批量单次请求，稳定性优先；批量合并为 P1 优化）；失败条目保留原值并 toast 提示。
  - 汇总条**本地实时计算**（不依赖 AI）：摄入 Σ = Σ餐食热量（自由餐不计）；消耗 Σ = Σ运动消耗；预计缺口 = 基础消耗 + 消耗 Σ − 摄入 Σ，按 FR4.6 阈值着色（300~800 绿）。
- **删除**：🗑 按钮 + toast 撤销（5 秒内有效）。
- 「确认完成，开始用」→ Step5；「返回修改」→ 回 Step2（草稿保留）。

### Step5 完成

- 执行**现有** `importPlan(draft)`：增量合并 + `applyMeta`（吸收 tdee/dailyCalorieTarget）+ `fullReschedule`（当日/次日提醒立即调度）——全部现成能力，store 零改动。
- 置 `onboardingState.done = true`，`uni.redirectTo` 首页，toast「🎉 计划已就绪，到点我会提醒你」，完成页附「查看使用指引 ›」入口（引导页内 UI，指向指引页）。
- 后续使用与现有流程完全一致，**不新增任何页面内轻引导、不弹任何提示卡**；加餐/加练的引导由使用指引归档承载（§5）。

## 9. 边界与异常场景

| # | 场景 | 处理 |
|---|------|------|
| 1 | 老用户升级到新版本 | isLegacyUser 命中 → 静默置 done，永不弹引导 |
| 2 | 引导中途杀 App | 基础信息已保存（Step1 即经 settings.update 持久化）；计划草稿丢失，重进引导 Step1 预填后重新走 Step2 |
| 3 | 用户点「跳过」 | 置标记不再弹；新用户可从设置 → 使用指引回看全部教程；今日页行为与老版本完全一致 |
| 4 | AI 未配置 Key | 引导页自带配置弹层（D4），可「暂不」转纯手动模式（手填热量 / 自由餐） |
| 5 | AI 生成失败/超时 | 自动重试 1 次 → 中文错误 + 重试/转手动双按钮；输入文本保留 |
| 6 | AI 返回不合规 JSON | 过 normalizePlan 校验管线；字段自动补默认；无条目时视为失败 |
| 7 | 清空全部数据 | **不修改 clearAll**：done 仍为 true 不自动重弹；需要重走引导 → 使用指引 →「重新体验首次引导」（主动行为，语义清晰） |
| 8 | 已有计划时重跑「重新体验引导」 | 确认完成走增量合并（同 id 更新、新 id 追加），打卡记录保留 |
| 9 | 生成结果与目标摄入偏差大 | 汇总条缺口着色提示（红/橙/绿），编辑步引导微调，不强制 |
| 10 | 引导页物理返回键 | Step0/跳过确认弹窗「退出引导？下次还会出现」→ 确认退出不置标记；其他步骤返回上一步 |
| 11 | 重跑「重新体验引导」时已有基础信息/热量 | 引导页预填 `onboardingState.profile`（性别/年龄/身高/体重/活动量）与已存热量（`settings.bmr>0` 时直读 BMR/TDEE/目标摄入，保留自定义目标；否则按完整 profile 重算），不出现空数据 |

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| AI 结构化输出不稳定（整日一句话模式字段多） | 中 | 复用校验管线 + 自动补默认 + 重试一次 + 手动模式永远兜底 |
| H5 截图与 App 真机视觉差异 | 低 | 截图时避开差异区域；不可接受时改真机截图（流程仅多传图一步） |
| 引导流程增加上手成本 | 中 | 全程可跳过可返回；Step 数控制在 3 步主流程；每步默认值齐全（减少输入） |
| token 成本（生成计划单次约 1~2k tokens） | 低 | 复用现有用量统计展示；重估仅对 dirty 条目发起 |
| ai.js 追加改动引发回归 | 低 | 追加区与现有函数物理隔离（文件末尾），不改签名不改行为；真机回归用例仅需覆盖现有 AI 功能不受影响 |

## 1. 项目背景与目标

用户已有完整的减脂餐计划与运动计划（由 AI 生成，见 `减脂餐.md` / `运动计划.md` 样例），但执行中存在两个痛点：

1. **忘记执行**：到了饭点/训练时间想不起来该吃什么、该练什么；
2. **加餐失控**：额外吃了外卖/KFC 后，不知道当天热量缺口还剩多少。

**产品目标**：做一个安装在安卓手机上的单机 App（Flutter 开发，v2.0 起；早期为 uni-app，已整体迁移），只做三件事——**导入计划、到点提醒、打卡**，外加**热量缺口计算**。界面简洁，离线优先，无账号无云端。

**明确不做**（控制范围）：
- 不内置自有 AI 服务（所有 AI 能力——计划文档转 JSON、食物热量查询——均通过用户自配的 API Key 实现）
- 不做账号系统、云端同步、社交功能
- 不做 iOS（v1 只打安卓包）
- 不做复杂的饮食/运动数据库管理（内置一份常见食物热量表即可）
- 不在现有页面内新增轻引导/提示卡/文案改动——引导能力只存在于引导页与使用指引页（F7/F8 范围硬约束）

## 2. 用户与使用场景

单一用户（本人），单机使用。

| 场景 | 描述 | 涉及功能 |
|------|------|----------|
| S1 首次导入 | 找 AI 生成计划 JSON → 复制 → App 内粘贴导入 → 预览确认 | 计划导入、模板 |
| S2 日常执行 | 12:00 收到通知「该吃午餐：冻豆腐虾仁荞麦面」→ 打开 App → 打卡 | 提醒、打卡 |
| S3 傍晚训练 | 18:30 收到通知「适应期·快走训练」→ 完成后打卡 | 提醒、打卡 |
| S4 下午加餐 | 16:00 提醒加餐 → 吃了水煮蛋 → 打卡（计划内，100 kcal） | 提醒、打卡 |
| S5 自由餐热量 | 周六吃了 KFC 套餐 → App 搜「香辣鸡腿堡套餐」→ 记录 1100 kcal → 查看当天缺口 | 食物库、加餐、缺口 |
| S6 外卖热量 | 点了份黄焖鸡外卖，库里搜不到 → AI 联网查询热量 → 确认记录 | AI 查询、加餐 |
| S7 复盘 | 周日查看本周打卡情况和每天热量缺口 | 统计 |
| S8 换计划 | 计划到期/不满意 → 重新找 AI 生成 → 再次导入覆盖 | 计划导入 |
| S9 首次使用 | 新装打开 App → 引导填基础信息算出每日基础消耗 → 录入饮食计划（逐条 / 整日一句话）→ AI 生成 → 编辑确认 → 进入正常使用 | 首次使用引导（F7） |
| S10 想学功能 | 加餐/加练/提醒收不到/统计不会看 → 设置 → 使用指引 → 图文教程（真实截图）随时回看 | 使用指引（F8） |
| S11 记体重 | 每天早上称重 → 设置 → 体重记录 → 录入 68.5 → 基础消耗按新体重更新，历史缺口不变；日历/详情看到每天的体重与基础消耗 | 体重记录（F10） |
| S12 临时改餐 | 中午没吃计划餐，点了外卖黄焖鸡 → 今日页点该餐 ✎ → 食物内容改成「外卖黄焖鸡米饭一份」→ AI 测算 640 → 保存（该条标「已改」，与计划脱钩）→ 打卡；之后换新计划/清空计划，历史这天的 640 依旧不变 | 条目快照（F11） |
| S13 临时改练 | 晚上没按计划快走，改跑 5 公里 → 今日页点该运动 ✎ → 运动内容改成「慢跑 5 公里」→ AI 按内容+体重测算消耗 350 → 保存（标「已改」）→ 打卡；之后清空运动计划，历史这天的 350 依旧不变 | 条目快照（F11） |

## 3. 功能需求

优先级说明：P0 = v1.0 必须完成；P1 = 后续版本可选增强。

### F1 计划导入（P0）

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR1.1 | 粘贴 JSON 导入 | 输入框粘贴 JSON → 解析校验 → 预览 → 确认后生效 |
| FR1.2 | 文件导入 | 可选择手机本地 `.json` 文件导入（同等校验流程） |
| FR1.3 | 格式校验 | 按 [import-format.md](import-format.md) 第 5 节规则校验，错误信息为中文并定位到具体条目/字段 |
| FR1.4 | 导入预览（全量查看与编辑） | 确认前显示：计划名、时间段、餐食 N 项、运动 M 项、每日目标热量；每个条目行内直接展示完整细节（餐食=食材清单 details/做法步骤 steps/备注，运动=训练内容 content 各环节名·具体内容·分钟数/注意事项），点条目弹全量编辑器可改（餐食：名称/类型/时间/热量/食材清单/做法步骤/备注；运动：名称/时间/时长/预计消耗/训练内容/注意事项），条目可删；预览中的全部增删改在确认导入时生效（确认导入以预览数据为准） |
| FR1.5 | 增量导入 | JSON 含 `meals` 则增量合并餐食计划、含 `exercises` 则增量合并运动计划（相同 id 更新该项，新 id 追加到列表末尾，另一模块不受影响）；`meta` 中的 tdee/dailyCalorieTarget 写入设置 |
| FR1.6 | 导入后即时生效 | 今日页立即按新计划渲染；当日未过期的提醒立即重新调度 |
| FR1.7 | 内置模板 | 模板页展示 JSON 格式说明 + 完整示例（template.json）+ AI 提示词，均可一键复制 |
| FR1.8 | AI 智能导入（主推） | 粘贴计划文档（Markdown/纯文本/聊天记录）→ 调用用户自配 AI 转 JSON → 校验 → 预览 → 导入；未配置 Key 时弹出 AI 配置弹层（页内填 Key，保存后立即继续原操作） |
| FR1.9 | 入口整合 | 导入页双模式切换：「✨ AI 生成（默认）」+「手动 JSON」（粘贴/文件/格式说明/模板合并入口）；计划页主按钮直达 AI 导入 |

### F2 到点提醒（P0）

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR2.1 | 本地通知 | 按计划项的 `time` 发系统通知：标题区分「用餐提醒/运动提醒」，内容含名称与简短备注 |
| FR2.2 | 提前量 | 全局可设提前 0/5/10/15/30 分钟提醒，默认 0 |
| FR2.3 | 开关 | 全局总开关；单个计划项可关闭（`reminder:false` 或详情页切换） |
| FR2.4 | 离 App 生效 | App 退到后台或被杀进程后，当天已调度的提醒仍能到达 |
| FR2.5 | 点击跳转 | 点击通知打开 App 并定位到今日页对应计划项 |
| FR2.6 | 调度时机 | App 启动/回到前台、导入成功、修改提醒设置后，自动重算今日+明日提醒 |
| FR2.7 | 省电引导 | 设置页提供国产 ROM 自启动/电池白名单的图文引导（不保证全自动跳转） |

已知限制（如实告知用户，见 design.md 第 8 节）：手机重启后需打开一次 App 恢复调度；部分 ROM 极端省电策略可能拦截，需加白名单。

### F3 打卡（P0）

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR3.1 | 逐项打卡 | 今日页每个餐食/运动项有打卡按钮，点击即记录（含时间戳） |
| FR3.2 | 取消打卡 | 当日内可再次点击取消；历史日期只读不可改 |
| FR3.3 | 打卡状态可视化 | 已打卡项有明显视觉反馈（对勾+变色）；今日页显示完成进度（如 3/5） |
| FR3.4 | 连续打卡 | 统计页显示连续完成天数（当日计划项全部打卡才算一天完成；今日加餐不参与完成度） |
| FR3.5 | 打卡持久化 | 数据本地持久化，卸载重装前不丢失（重装丢失可接受，v1 无导出） |
| FR3.6 | 当日实际热量 | 每餐可 ✎ 调整「今日实际摄入」（覆盖计划值，含备注），仅当天生效，明天自动恢复计划值；打卡后按实际值计入缺口 |
| FR3.7 | 实际热量 AI 估算 | 调整弹窗内大白话描述（如"没买到豆浆只吃了包子"）→ AI 估算总热量并展示拆解，确认后填入 |

### F4 加餐与热量缺口（P0）

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR4.1 | 今日加餐（唯一计划外入口） | 加餐页三方式录入：内置食物库搜索 / AI 估算 / 手动；**添加即计入缺口**（无需打卡），仅当天有效，明天自动消失，不影响整体计划与完成度 |
| FR4.2 | 内置食物库 | 离线搜索常见食物：KFC 单品/套餐、麦当劳、常见外卖（黄焖鸡/麻辣烫/炒饭/螺蛳粉等）、饮品零食，约 70 条种子数据 |
| FR4.3 | AI 联网查询 | 库里搜不到时，调用用户自配的 AI API（OpenAI 兼容协议，DeepSeek 默认）查询食物热量，返回结构化结果供确认（热量可编辑） |
| FR4.4 | 加餐管理 | 今日加餐列表（今日页 + 加餐页）可删除单条，热量从缺口中扣回；来源标记（食物库/AI/手动） |
| FR4.5 | 缺口计算 | 今日页实时显示：目标摄入 / 已摄入（已打卡餐实际值+今日加餐）/ 运动消耗 / **热量缺口**；缺口 = (TDEE + 运动消耗) − 已摄入 |
| FR4.6 | 缺口着色 | 缺口 < 0 红色（超标）；0-300 橙色；300-800 绿色（推荐区间）；> 1000 橙色（过猛提示） |
| FR4.7 | 自由餐补录 | `calories:null` 的计划项打卡后，提示「去记录实际热量」（✎ 调整或 AI 估算） |

|------|------|----------|

| FR5.5 | 某日详情 | 统计页月历/周图点击任意一天（含未来、开始前）弹层查看：完成度 n/m、已摄入、缺口 + 当日逐项清单（计划餐打卡状态与实际热量、临时加餐、运动消耗）；未来的日期显示计划安排（摄入 —、缺口「待开始」，不产生假缺口），开始前显示「计划开始前，无统计数据」 |
| FR5.6 | 月度回顾 | 月历标题旁「月回顾」入口弹层：计划完成天数、总缺口、日均缺口 + 有记录天数；展示「消耗最多的一天」与「摄入最多的一天」，各显示当天**热量缺口、总摄入、总消耗**（缺口正绿/负橙着色，消耗最多的一天注明基础+运动拆分）；每张卡片带「查看详情」按钮，下钻某日详情弹层（FR5.5）查看当天逐项条目，关闭后回到回顾层；只统计开始日后、今天前有记录的日子，本月无记录显示空状态 |

### F7 首次使用引导（P0，v1.1 增补）

设计依据：[guide-design.md](guide-design.md) v0.2（已评审）。**范围硬约束（只增不改）**：除 FR7.13 列出的最小接入点外，现有功能与页面交互零修改。

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR7.1 | 首启自动触发 | 新装首次打开自动进入引导页；完成后/跳过后不再自动出现（`onboardingState.done` 判定，独立存储键）；中途退出不置位，下次启动仍可继续引导 |
| FR7.2 | 老用户升级豁免 | 升级安装时检测：有计划 / 有打卡记录 / bmr>0 / 配过 AI Key 任一命中 → 静默置 done，永不弹引导 |
| FR7.3 | 欢迎页与跳过 | Step0 展示产品三能力卡；「跳过」置 done 直接进首页，现有页面行为与改前完全一致 |
| FR7.4 | 基础信息与基础消耗 | 引导内填写性别/年龄/身高/体重/日常活动量，实时显示：基础代谢 BMR、每日基础消耗（BMR×1.2，不含运动）、参考总消耗（BMR×活动系数）；公式与设置页估算器一致（复用 `estimateBmr`，Mifflin-St Jeor） |
| FR7.5 | 保存口径 | 「保存并继续」经现有 `settings.update()` 写入 tdee（=基础消耗）/ bmr / dailyCalorieTarget，与设置页同路径同口径；基础信息存 `onboardingState.profile`（settings 不加字段） |

### F10 体重记录与基础消耗按日沿用（P0，v1.4 增补，App v1.0.2 已实现）

设计依据：[weight-design.md](weight-design.md) v1.0。核心原则：**历史日期的基础消耗一旦成为事实就不再变化，新值只从生效日起应用**。范围约束（只增不改）：引导页/今日页布局/guide 教程/计划结构/提醒调度零改动，改动清单见 weight-design.md §8。

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR10.1 | 体重录入 | 设置页「热量」分组新增「体重记录」行 → 弹层录入今日体重（30.00–300.00 kg，允许两位小数如 68.55）；同日重复录入覆盖；仅支持当天，不支持历史补录 |
| FR10.2 | 体重记录持久化 | 新存储键 `weightRecords`：`{ baseline, records: { date: { weight, bmr, updatedAt } } }`；一天一条；BMR 在录入时按当时基础信息快照，后续基础信息改动不影响已录入日期；不参与 400 天裁剪 |
| FR10.3 | 历史缺口稳定（Bug 修复，最高优先） | 录入体重/估算器改 bmr·tdee 后，**所有历史日期的基础消耗与缺口逐日完全不变**；变化仅从生效日起应用。机制：① `baseBurnForDate` 按日沿用（最近 ≤当日体重记录的 BMR×1.2 → 基准固化值 → 现状口径 fallback）；② 首次录入体重或 bmr/tdee 即将变化且本机有历史记录时，固化当时基础消耗为 `baseline`（含固化日，幂等） |
| FR10.4 | 基础信息联动 | 基础信息（性别/年龄/身高，来自引导/热量设置）完整时，录入体重即时算出 BMR 并同步 `settings.bmr`；**同步 `profile.weight` = 本次体重**（设置页「基础信息」行与体重记录两处保持一致；profile 全空时不写半截数据）；不完整时记录 `bmr=0`（仅展示体重，不影响基础消耗）并提示去「热量设置」补全 |
| FR10.5 | 日历展示 | 月历中**有体重录入**的格子数字下方小字显示体重；某日详情弹层统计行增加「体重」格（未录入的天沿用最近一次记录，无任何记录显示「未记录」），并新增「基础消耗 N kcal · 运动消耗 M kcal」核对行；未来日期显示「—」 |
| FR10.6 | 运动消耗 AI 结合个人基础信息 | `estimateBurn` 携带性别/年龄/身高/体重（当天生效体重优先于引导 profile），系统提示词按运动强度结合资料估算，未提供体重按 65kg 兜底；覆盖今日页「AI 算」与统计页补录锻炼两个入口，返回结构不变 |
| FR10.7 | 备份与数据管理 | 备份快照 → 10 项（+dayEntries+weightRecords，formatVersion 2，与 FR11.10 同一口径；appVersion 1.0.2）；增量导入记录按 updatedAt 取较新、baseline 取固化日较早者；覆盖导入整体替换；清空全部数据一并清空；导入概要显示体重条数 |
| FR10.8 | 口径不回归 | 体重录入不记入打卡天（不影响连续打卡/完成度/月历着色）；计划项 caloriesBurned 维持计划静态值不被 AI 重算 |

### F11 当日条目快照与历史固化：餐食 + 运动（P0，v1.5 增补，App v1.0.2 已实现）

设计依据：[day-snapshot-design.md](day-snapshot-design.md) v1.2。核心原则：**计划 = 模板，当天打卡 = 快照事实**——每天把计划餐与计划运动实例化为当日条目（统一 DayEntry 模型，kind 区分），修改即脱钩，历史统计只读快照；删除/清空/覆盖任何计划，历史记录逐项不变。与 F10 同为「历史固化」哲学（F10 固化每日基础消耗，F11 固化每日条目内容）。

| 编号 | 需求 | 验收标准 |
|------|------|----------|
| FR11.1 | 条目三字段 | 每条当日条目 = **内容**（多行文本）+ **热量**（kcal，可空=待补录）+ **备注**；餐食内容=食物内容（计摄入），运动内容=运动内容（计消耗）；今日页卡片主行显示内容，子行显示热量与备注摘要 |
| FR11.2 | 计划套用（实例化） | 进入当天/计划变更时把当天计划餐与计划运动实例化为快照条目：内容=计划名、热量/消耗=计划值、时间与分类跟随计划；未来日期不生成快照，仅渲染计划预览 |
| FR11.3 | 修改即脱钩 | 编辑内容保存后该条与计划脱钩：卡片标「已改」、不再显示划线计划值、不再跟随计划变化（热量/备注修改不脱钩，维持当日覆盖语义）；脱钩条目仍参与当日完成度 |
| FR11.4 | AI 按新内容重测 | 编辑弹窗「✨ AI 测算」对当前内容+备注直接测算（餐食→estimateMeal 总热量，运动→estimateBurn 消耗、结合体重等个人资料）并展示拆解，确认后回填；餐食提示词改为通用「这一餐实际吃了什么」；未配置 Key 时弹配置层、配好后继续（沿用现状） |
| FR11.5 | 恢复计划内容 | 脱钩条目且对应计划项仍在时，编辑弹窗提供「恢复计划内容」一键复位：内容/热量恢复计划值、备注清空、解除脱钩（餐食与运动同构） |
| FR11.6 | 计划变更同步（仅今天） | 导入计划/编辑/删除计划项/分模块清空（餐食或运动）后仅同步当天快照：未脱钩条目跟随计划（热量未被手改则跟随）、失效的未脱钩条目移除、新条目追加、**脱钩条目永不改动**；历史快照不触碰 |
| FR11.7 | 历史固化（最高优先） | 删除计划项/清空餐食或运动计划/增量或覆盖导入后，历史日期的完成度、已摄入、运动消耗、缺口、某日详情逐项与操作前完全一致；快照层 dayEntries 不参与 400 天滚动裁剪 |
| FR11.8 | 计划外录入统一 | 手动/食物库/AI 的加餐与加练（含统计页历史日期补录）写入快照层（source 标记保留），添加即计缺口、可删除，语义与现 tempTasks 一致；tempTasks 停写退役（模型与 v1 备份兼容保留） |
| FR11.9 | 存量迁移（升级首启） | 升级后首启把本机有记录的历史日期实例化为快照（打卡状态沿用 checkRecords、mealAdjust 覆盖值→餐条目、tempTasks 全量→计划外条目、计划运动→运动条目），幂等；**与 FR11.10 的 v1 备份转换共用同一套转换核心**；迁移后历史统计完全走快照路径 |
| FR11.10 | 备份兼容与旧格式转换 | 备份快照 9 项 → 10 项（+dayEntries），formatVersion 升 2；**v2 备份照常导出旧键（旧版 App 也能读，双向不锁死）**；导入 v2 按「同 id 合并、新 id 追加、导入优先」；**导入 v1 老备份在导入管线内直接转换为快照格式（用备份内 planData 投影），不依赖启动迁移**——换机新装导入旧备份后历史立即固化可用；同一备份重复导入幂等不重复；FR9.5「历史统计可能变化」风险提示随之移除；自动备份沿用现有触发机制（dayEntries 变更计入防抖信号） |
| FR11.11 | 口径不回归 | 打卡状态仍记入 checkRecords（键空间不变）；完成度只统计计划来源条目（含脱钩）；计划外加餐/加练不计入完成度、添加即计；计划运动消耗=快照值（打卡计入）而计划项 caloriesBurned 本身不被 AI 重算（FR10.8 延续）；提醒调度、计划结构、导入格式（import-format.md）零改动 |
